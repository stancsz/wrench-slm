02 / 它怎么干活

小事在本地做，
做完还得过检查。

把 Wrench 想成开发流程里的一个小帮手：只接范围清楚、结果能验的活儿。接不住的，就原样交回去。

拿一个常见场景来说

你让编程助手查一个超时问题。查明原因需要推理，但中间可能有一步，只是读一下配置。Wrench 就负责这一步：找到配置、校验请求、把原始信息带回来。至于整个故障怎么诊断，仍由外层工作流负责。

少调一次模型，不等于整单就省钱了。准备任务、检查结果、失败重试都得算进去。最后同样的活儿得干成，账才有得比。

和 coder 模型有什么不同，怎么做到“更能扛事情”？

Wrench 为配合大模型、降低整条工作流的成本而做。Coder 模型通常面向更完整的编程任务，也能调用工具、利用测试反馈。Wrench 则把范围收窄到其中能明确描述、独立检查的小步骤。两者可以一起用。

任务Coder / 大模型负责Wrench 接住的部分
排查登录超时形成假设，判断根因，提出修复。按明确请求读取配置、查找报错原文。
准备代码修改决定修改方案，处理跨文件依赖。在支持范围内准备有边界的补丁草稿，交给人或外层流程审阅。
处理很长的历史结合相关证据继续推理。检索路径、符号和相关片段，保留可追溯的出处。
遇到不确定或越界请求由外层流程决定进一步推理、询问或停止。明确 abstain，交回控制权，不自行扩大权限。

“能扛”要落在具体机制上：明确参数用程序构造，操作由独立验证器把关，执行有权限边界，结果能追溯，失败有交接。这些机制减少自由生成和无边界执行的空间。普通 coder 也可以配类似的系统；Wrench 的价值必须体现在把这套分工做好，并测出收益。

Abstain 是交接机制，不能拿拒绝率当成绩

它的意思是：“这一步不在我的能力或权限范围内，或者没通过检查，请调用方接手。”它是程序能识别的结果，不是一句含糊的“我可能不会”。调用方保留原任务，再按配置安排更强模型或其他处理方式。

目前，这个决定主要依靠明确规则和验证边界，不能宣传成模型已经学会准确判断自己的信心。学习式自由路由仍然关闭。如果什么都拒绝，只是多绕一圈调用大模型，反而可能更慢、更贵。

因此，我们要一起看：该接的小任务做对了多少，本该拒绝的有没有误放行，最终任务有没有成功，以及把检索、校验、重试和兜底全算进去后，耗时和成本到底有没有下降。对照还要包含“简单规则 + 大模型兜底”，确认 Wrench 多出来的部分真的有用。当前证据和验收边界在这里。

关于 coder 模型也具备 agent 和工具调用能力，可参考 Qwen3-Coder 官方介绍。上表描述我们的任务分工，不是模型性能排行榜。

一条请求会走哪些步骤？

  1. 收下任务和允许的范围。先分清你现在要干什么，别被旧上下文带跑。
  2. 找相关材料。通过本地搜索和检索，缩小后续要处理的内容。
  3. 提出一个有边界的操作。明确的机械任务可以走固定规则。目前不启用模型自由决定路线的功能。
  4. 独立校验。操作类型、目录、参数、数量限制，都要先过关。
  5. 交结果，或者明确拒绝。客户端把提案与经过校验的结果、最终回答关联起来。处理不了时，由外层工作流决定怎么交给备用模型。

这些工具各干什么？

工具名用人话说边界在哪
read_file读一个小文本文件。限定目录和字节数。
read_lines只读指定的几行。行号范围要明确。
literal_search原样找一段文字。限制结果数，不是任意正则执行器。
git_read_status看看工作区状态。不会 commit，也不会 push。
health_read看看允许的本地服务是否正常。仅限回环地址和允许的健康检查路径。
patch_draft写一份补丁草稿给你看。不会替你应用补丁。

钥匙给到哪儿，就到哪儿

Wrench 没有任意 shell 执行、自动写入或凭据访问操作。开发新功能、迁移数据库、部署服务、跨文件多步调试，都不在这个小帮手的职责里。

abstain 就是“这单我在当前权限内接不了”。它是交接信号，不算任务已经完成。调用方需要保留原请求，并明确安排后续处理。

允许访问的目录是你划的真实边界。评估时请用单独、不含敏感内容的测试目录。文件读取器不会自动替你识别所有秘密；启用云端备用模型时，也要看看客户端会把哪些上下文发出去。

“大上下文”在这里是什么意思？

先在一大堆输入里检索、整理，再把相关部分压到有限的工作上下文里。它不代表一个小模型能同时注意几百万个 token，也不代表整座代码仓库的细节都被吃透了。
