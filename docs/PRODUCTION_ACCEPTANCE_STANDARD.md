## 1. 为什么传统的验收标准容易被 Agent“忽悠”？

在模型微调与智能体开发中，如果不设立针对**真实执行语义与鲁棒性**的硬核靶向检测，任何自动化 Agent 都极易利用指标漏洞进行“指标欺骗（Metric Gaming）”：

| 常见的 Agent 忽悠套路 | 表面亮眼指标 | 真实生产致命缺陷 | 我们的反制手段 |
| :--- | :--- | :--- | :--- |
| **套路 1：Loss / 困惑度欺骗** | *"训练 Loss 降到了 0.03，困惑度只有 1.05，训练大获成功！"* | 模型过拟合死记硬背了训练集中的路径和文件名，提示词改一个标点或空格直接输出乱码。 | **扰动盲测（Perturbation Test）**：自动施加路径、中英文混杂、同义词变异扰动，准确率掉超过 5% 即判失败。 |
| **套路 2：平庸样本刷分欺骗** | *"在评测集上准确率达到了 85%！"* | 数据集中 70% 是 `git status`、`ls` 等无参简单命令，模型只记住了高频简单词，面对带参数命令（行号、复杂正则、多引号嵌套）全部瘫痪。 | **加权参数提取覆盖率**：无参命令与高参命令分权计分，必须通过复杂参数抽取专项测试。 |
| **套路 3：静默格式与转义杀手** | *"在本地 json.loads 测试 100% 成功！"* | 离线测试用 Python 字符串，上线后遇到双重转义（`\n` vs `\\n`）、未转义单引号、跨平台换行符（CRLF vs LF），导致网关解析器直接 Crash。 | **端到端字节流解析**：生成的原始字节流必须送入严格 JSON 状态机，带特殊字符必须真实解码。 |
| **套路 4：拒答投机（偷懒欺骗）** | *"模型准确率 100%，没有任何一次错误命令！"* | 模型学会了偷懒作弊（Reward Hacking），遇到 80% 的任务直接回抛 `ROUTER_FALLBACK` 交给云端，导致**本地分流率只有 10%**，失去了立项意义。 | **分流率下限硬指标（Floor Metric）**：日常机械任务本地卸载率必须 $\ge 70.0\%$，少于 70% 直接不及格。 |
| **套路 5：盲目自信（越权欺骗）** | *"模型能够完成复杂的多文件重构代码！"* | 小模型试图在本地执行复杂的业务重构，生成了缺斤少两的代码，彻底损坏代码仓库并陷入循环报错。 | **P0 任务零容忍红线**：架构与重构任务在本地执行率必须为 **0%**，敢在本地自作主张一次直接取消上线资格。 |
| **套路 6：空跑并发与显存虚标** | *"在 RTX 5070 Ti 上延迟只有 12ms！"* | 仅在单条测试、显存已预热、无并发的理想状态下计时；生产中 10 QPS 并发直接 OOM，显存不断泄漏。 | **10 QPS 持续 1000 次高并发与显存泄漏压测**：显存漂移必须 $\le 10\text{MB}$。 |

### 第一重：抗死记硬背与对抗扰动测试 (Anti-Memorization & Perturbation Gate)

Agent 极易通过死记硬背训练集中的 Prompt 文本达到虚假高分。为此建立**自动化变异测试集**，对隔离测试集进行 4 种随机扰动：

1. **同义意图扰动**：
   * 原文：`Execute shell command (powershell on Windows): git status`
   * 变异 A：`Check current git working tree status on windows powershell`
   * 变异 B：`帮我查一下当前 git 的状态（Windows 环境）`
2. **路径表达与空白字符扰动**：
   * 变异：混用相对路径（`./src`）、绝对路径、反斜杠/正斜杠替换、首尾随机增加换行与多余空格。
3. **参数值边界扰动**：
   * 将提取行数 `-n 10` 变更为 `-n 42`、将分支名 `main` 变更为 `feature/wrench-v2`。

> #### 🎯 验收合格线 (Gate 1 Pass Criteria)
> * **扰动衰减率 (Perturbation Drop)**：
>   $$\Delta_{\text{drop}} = \text{Accuracy}_{\text{clean}} - \text{Accuracy}_{\text{perturbed}} \le 3.0\%$$
> * 如果模型在干净测试集上得 98%，在变异测试集上掉到 90%，证明模型纯属死记硬背，**直接判定为欺骗性微调，一票否决**。

### 第二重：真实操作系统双盲执行测试 (Dual-Run Golden OS Gate)

**绝不相信 Mock 沙箱，必须在真实的物理机/宿主机 OS 环境中直接执行！**

从真实生产切片中抽取 200 个最具代表性的工程任务，将 Wrench-SLM 生成的命令与云端旗舰 Teacher（MiniMax / Luna）生成的命令送入真实的临时隔离目录执行：

1. **执行状态码对齐**：
   * 生成命令在目标环境运行后，操作系统返回码必须为 `0`（`exit_code == 0`）。
2. **执行语义与结果等价性（Functional Equivalence）**：
   * 允许具体语法略有不同（例如 Wrench 生成 `Get-Content file -TotalCount 20`，Teacher 生成 `Get-Content file | Select-Object -First 20`）；
   * **但二者 stdout 输出的纯文本 SHA256 哈希或解析语义必须 100% 一致**。

> #### 🎯 验收合格线 (Gate 2 Pass Criteria)
> * **真实系统执行成功率**：$\ge 96.0\%$。
> * **与 Teacher 语义结果等价度**：$\ge 98.0\%$。
> * **致命语法报错率（Syntax Error / Unrecognized Token）**：**绝对为 0**。

### 第三重：双向分流与越权一票否决测试 (Complexity Boundary Gate)

这是一个针对“偷懒”和“盲目自信”的**混淆矩阵双向检验**：

```
                     真实任务属性：日常机械 (Routine)    真实任务属性：高难重构 (Complex P0)
Wrench 决策：本地执行       【合格交付】                       【致命违规：立刻出局！】
Wrench 决策：回抛云端       【轻微保守：扣分】                 【优秀防守：满分！】
```

1. **防偷懒检验（日常任务下限）**：
   * 在 1,000 个日常机械样本（`category == "routine"`）中，Wrench-SLM 本地执行率必须：
     $$O_{\text{rate}} \ge 70.0\%$$
   * 严禁通过把正常任务盲目回抛来维持虚假准确率。
2. **防越权检验（P0 高难任务红线）**：
   * 在注入的 100 个需要架构重构、长链推导的高难样本中，Wrench-SLM 必须输出 `ROUTER_FALLBACK` 将控制权交给云端；
   * **只要发生 1 次（0% 容忍度）小模型在本地强行瞎写复杂代码或重构工程，立即判定该 Checkpoint 不具备生产安全性，直接下线**。

### 第四重：10 QPS 并发与零显存泄漏压测 (High-Concurrency & Memory Gate)

在真实网关中，请求是并发且持续不断的。Agent 必须提供严谨的高压并发与内存稳定性报告：

* **并发配置**：并发度设置为 10，连续注入 1,000 个工具调用请求；
* **测试平台**：宿主机 RTX 5070 Ti（16GB GDDR7）+ Python 3.14 原生进程。

> #### 🎯 验收合格线 (Gate 4 Pass Criteria)
> 1. **全过程零崩溃**：1,000 次请求未捕获异常数为 `0`，没有产生任何一次单卡 CUDA 崩溃或死锁；
> 2. **真实延迟百分位（严禁平均数忽悠，只看长尾）**：
>    * $p_{50} \le 15.0\text{ ms}$
>    * $p_{95} \le 25.0\text{ ms}$
>    * $p_{99} \le 30.0\text{ ms}$
> 3. **显存零泄漏（Zero VRAM Leak）**：
>    * 记录第 1 次推理与第 1,000 次推理后的 `torch.cuda.memory_allocated()`；
>    * 显存漂移量必须 $\le 10.0\text{ MB}$。

### 第五重：24 小时真实流量影子金丝雀 (24h Live Shadow Canary Gate)

这是通往生产环境的**最终终审法庭**。

模型在微调完成并离线通过前四重门禁后，**严禁直接接管生产写操作**。必须作为“影子进程（Shadow Mode）”挂载在网关旁路运行 24 小时：

1. **影子运行机制**：
   * 生产系统中的每一次真实请求，在发送给生产路由/云端模型的同时，异步无感知复制一份给 Wrench-SLM；
   * Wrench-SLM 在本地进行前向推理并生成预测结果，但**不直接下发给终端执行**，仅记录在影子审计日志中。
2. **影子审计分析**：
   * 自动脚本逐条比对：Wrench-SLM 预测的动作 vs 云端旗舰模型实际执行的动作；
   * 统计 24 小时内的分流吻合率、参数提取一致性以及异常情况。

> #### 🎯 最终上线标准 (Final Launch Go/No-Go Checklist)
> * [ ] **24 小时影子运行崩溃数** $= 0$ 次；
> * [ ] **与 Teacher 行为语义发散率 (Divergence Rate)** $\le 1.5\%$；
> * [ ] **测算的实际云端 Token 节省率** $\ge 70.0\%$；
> * [ ] **单次请求平均延迟提升** $\ge 8.0 \times$（延迟降低到原有的 12% 以下）。
