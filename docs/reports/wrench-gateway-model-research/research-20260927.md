## Research question

What small model can live on this host as a Wrench gateway, learn Wrench's
bounded work style through LoRA, complete at least 95% of tasks locally, send
no more than 5% to a frontier model, and reduce frontier tokens by at least
95% versus the same frontier-only workload, while preserving verified task
outcomes and supporting sustained software engineering?

## Recommendation

Build a **deterministic gateway first, with one small LoRA decision model and a
strong-model fallback**. Do not make the LoRA the general coding agent.

1. Deterministic Wrench code owns exact reads/search, token budgets, context
   assembly, source IDs, reversible summaries, schema validation, diff checks,
   audit receipts, and stop conditions.
2. The LoRA controller may choose among finite context policies, known evidence
   IDs, retrieve/stop/abstain decisions, and a local-versus-frontier route. Its
   answer is only a proposal. The host validates every field and source ID.
3. The stronger coding model remains responsible for diagnosis, architecture,
   multi-file semantic edits, test repair, ambiguous requirements, and any
   task where Wrench cannot establish enough evidence.
4. Compression should discard only content that can be fetched again from an
   exact source snapshot. Preserve user instructions, active diffs, hot code,
   failure output, and provenance exactly. A generated summary never replaces
   source-of-truth bytes.

This is the most realistic way to reduce paid context and mechanical work while
preserving engineering quality. The honest small-model target is a narrow
controller for retrieval, source-linked context selection, bounded compaction,
and abstention. It is not a standalone all-day software engineer. Qwen labels
0.8B for prototyping and task-specific fine-tuning, and warns that thinking mode
can enter loops; keep it in short, schema-bounded non-thinking calls unless
Wrench-specific evidence justifies another setting.

## What the LoRA should learn

Use a fixed output schema with a short enum for `LOCAL_MECHANICAL`,
`LOCAL_COMPACTION`, `FRONTIER`, and `ABSTAIN`, plus selected evidence IDs,
retrieve/stop choice, and a compact reason code. Train on fresh Wrench-authored
synthetic scenarios with deterministic labels. The candidate may learn when
to preserve, retrieve, compact, or escalate; it may not invent evidence,
execute a tool, modify a file, grant permission, or redefine a safety policy.

The first comparison is deterministic policy versus frozen 0.8B versus the
same 0.8B with LoRA. This isolates whether adaptation improves the finite
Wrench decision. A downstream comparison later adds (a) the strong model alone,
(b) deterministic Wrench plus the same model, and (c) Wrench plus LoRA plus
that same model. No local model should be promoted merely because it emits
valid JSON or compresses a prompt.

## Exact meaning of the 95/5/95 target

Keep these results separate:

1. **Local completion rate**: verified task episodes completed without any
   frontier call divided by all episodes. The target is at least 0.95, with
   the lower confidence bound at or above 0.95. Keep every failed task in the
   denominator.
2. **Frontier escalation rate**: episodes with one or more frontier calls,
   including retries and auxiliary calls, divided by all episodes. The target
   is at most 0.05, with the upper confidence bound at or below 0.05. A 5%
   escalation share by itself does not show either task success or token
   savings.
3. **Frontier-token savings**: `1 - total_hybrid_frontier_tokens /
   total_frontier_only_tokens` across the same paired tasks. Sum actual input
   and output token usage for every call, retry, verification, compaction,
   fallback, and cache miss. The target lower confidence bound is at least
   0.95. If the provider does not return auditable usage receipts, mark the
   claim unmeasured.
4. **Hybrid task-success retention**: independently verified hybrid passes
   divided by direct-frontier-only passes on matched tasks. Require the lower
   confidence bound to be at least 0.95 and report severe failures separately.
5. **All-tier tokens and dollars**: report local tokens, frontier tokens,
   inference cost, local energy/compute, training cost, and amortized operating
   cost separately. Frontier-token reduction is not the same as total token
   reduction, 95% lower dollars, or 95% quality retention.
6. **All-in dollar savings**: `1 - hybrid_total_cost / frontier_only_total_cost`
   on the matched tasks, including provider charges, measured local energy,
   hardware/runtime allocation, training and evaluation amortization, and
   retries. If “95% cheaper” is literal, require its own lower confidence
   bound at or above 0.95. A 95% frontier-token reduction alone does not prove
   this cost claim.

Use actual provider usage receipts and a pinned model/tokenizer/cost schedule.
Keep failed Wrench tasks and every fallback in the totals. Compare identical
source snapshots, permissions, tools, task budget, stop rule and outcome
oracle. Context-size estimates, local token counts, route accuracy, and
synthetic prompt shortening are diagnostics, not proof of the target. For
OpenRouter, preserve raw usage fields and distinguish prompt-cache hits from
tokens sent; [usage and prompt-cache guidance](https://openrouter.ai/docs/guides/best-practices/prompt-caching)
and [response-cache behavior](https://openrouter.ai/docs/guides/features/response-caching)
need to be included in the measurement plan.

As a planning example, if task episodes were independent Bernoulli trials,
234 episodes would give 80% power at one-sided 5% significance to reject a
5% failure/escalation rate when the true rate is 2%; at that size, at most 6
events meet the exact one-sided 95% upper-bound test. This is not yet the
experiment sample size: repository and task-family clustering, paired quality
retention, dollar/token ratios, and the full-day objective need their own
pre-registered power calculation and likely a larger workload.

## Can it handle a developer's whole day?

The small gateway's role is to keep source evidence and context usable between
turns; the stronger model does the hard engineering. Prove this with a later
matched workflow study, not by running a short coding benchmark: multiple full
workdays or a preregistered equivalent queue, at least three unrelated
repositories and more than one language, with diagnosis, scoped features,
failing tests, refactors, dependency/API changes, review fixes, and long-context
recovery. Record test/CI outcomes, regressions, user corrections, retries,
latency, context loss, resource restarts, energy, spend and recovery. Use a
powered sample plan and keep repo/task-family/time groups separate.

Long-horizon coding benchmarks are useful task sources, not ground truth by
themselves. OpenAI's July 2026 audit of SWE-Bench Pro flagged 27.4% of tasks
with its analysis pipeline and 34.1% in its human annotation campaign, and
estimated roughly 30% had breaking issues. A September 2026 SWE-Bench Pro
Verified paper separately reports reward-hacking and task-quality concerns.
DeepSWE instead uses original tasks and hand-written behavioral verifiers; its
authors report independent-judge disagreement of 1.4% versus 32.4% for
SWE-Bench Pro's inherited tests. METR's Time Horizons estimates task-duration
reliability at a stated success probability. Together these motivate human
reviewed Wrench tasks, clean group/time splits, behavioral verifiers, and a
powered full-workday evaluation. None proves Wrench's all-day reliability.
See [SWE-Bench Pro](https://arxiv.org/abs/2509.16941), [OpenAI's SWE-Bench Pro audit](https://openai.com/index/separating-signal-from-noise-coding-evaluations/), [SWE-Bench Pro Verified](https://arxiv.org/abs/2609.08149), [DeepSWE](https://arxiv.org/abs/2607.07946), and [METR Time Horizons](https://metr.org/time-horizons/).

No retrieved model card or paper establishes that a sub-2B LoRA can work as an
independent software engineer all day. Wrench should test the small model only
on limited proposals. Deterministic code owns exact search, parsing,
verification, source identity and reversible compaction. A stronger coder

with unrelated repository snapshots and languages, real edit/test loops,
compaction plus source re-fetch, interrupted/restarted sessions, and outcome
review. Count timeouts, regressions, corrections, human rescue, calls, all
tokens and local compute. METR's task-horizon method also separates task

compute and LoRA training. SWE-Pruner's 23-54% interactive savings is a more

## Research update: model role, compaction, and proof closure (2026-09-27)

### Practical model decision

No public model card establishes that a sub-10B local model can independently
perform a complete developer workday at the requested success level. The
credible approach is a deterministic Wrench runtime plus a LoRA-trained small
controller for finite evidence and context choices, with a strong-model route
for diagnosis and semantic multi-file changes. Exact retrieval, context
budgeting, source IDs, parsing, and verification stay deterministic. A local
summary is a view over source-of-truth files, never a substitute for them.

The already-present Qwen3.5-0.8B remains the smallest baseline for its narrow
synthetic gateway screen, but its 0/10 general semantic screen does not support

48.8 versus 25.3 and 11.6 for 0.8B, respectively; these vendor numbers are

### Context compression and tool interface

LLMLingua-2 treats compression as token classification with a bidirectional
encoder, reporting 3x-6x compression-model speedups and 1.6x-2.9x end-to-end
latency speedups at 2x-5x compression on its benchmark set. This makes
extractive selection a research-backed alternative to free-form summarization,
but source-code fidelity is unproven. Wrench should compare exact retrieval,
source-linked compaction, and extractive token selection on paired tasks; test
regressions and exact-source recovery. Preserve active instructions, changed
lines, relevant tests, error output, and provenance.

The coding-specific [SWE-Pruner preprint](https://arxiv.org/abs/2601.16746)
reports a task-aware 0.6B line selector with 23%-54% token reduction on
multi-turn agent tasks including SWE-Bench Verified, sometimes improving
success. Its up-to-14.84x compression applies to single-turn LongCodeQA and
does not establish 95% savings over an iterative workday. It reinforces the
need for goal-conditioned line/span selection while keeping the exact sources
retrievable, not aggressive free-form code deletion.

An ACL 2026 study, “Don't Adapt Small Language Models for Tools; Adapt Tool
Schemas to the Models,” reports gains of up to 17% in tool selection and 80%
fewer nonexistent-schema-name errors from a training-free schema alignment
method on its benchmarks. For Wrench, keep deterministic canonical schemas and
model-specific schema mapping as controls. The LoRA remains necessary for
Wrench's bounded policy style (retrieve/stop/abstain/context-choice behavior),
but it should not be asked to learn arbitrary tool execution or authority.

The adapter target set should itself be tested. A 2026 component-placement
preprint trained Qwen3.5-0.8B with multiple LoRA placements: attention-only
used 24 modules and 1.08M trainable parameters, versus 186 modules and 10.82M
for all-layer adaptation. On its non-Wrench instruction/math tasks,
attention-only often matched or exceeded the full adapter; recurrent Gated
DeltaNet placements substantially degraded some task scores. In the code
domain, the broader placement was favored, yet all sub-1B placements had
HumanEval pass@1 <=0.6%. The authors report a single-seed setup, so treat this
as a strong reason for a Wrench ablation, not a guaranteed result. The current
Wrench runner uses an all-projection target list matching those 186 modules.
Since Wrench's narrow task is policy/evidence selection rather than code
generation, add a reviewed attention-only candidate (24 full-attention query,
key, value, and output projection modules) beside the current all-module
baseline, with identical train/dev data and no held-out tuning. Verify exact
candidate modules and PEFT attachment before either full fit. Do not infer
that adapter from the current all-module preflight. See [Where Should LoRA
Go?](https://arxiv.org/abs/2604.22127) and the [official Qwen3.5
Transformers implementation](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_5/modular_qwen3_5.py).

The full-day claim needs end-to-end issue episodes, not code-token benchmarks.
SWE-bench frames repository engineering as resolving real GitHub issues and
notes multi-file coordination, execution environments, long contexts, and
complex reasoning. The new workday design therefore requires paired clean
snapshots, actual edits and tests, recovery, human rescue accounting, and
independent acceptance checks. The [product proof design](../../evals/wrench-gateway-model-research/product-proof-design-20260927.md)
now sets numeric session gates and resolves the third review's required fixes:
LoRA arm only for primary claims, predeclared sampling frame and grouped/time
split, counterbalanced isolated workspaces, orthogonal outcome/route fields,
frontier-only escalation definition, simultaneous cluster-aware power plan,
cache-safe token accounting, complete labor/hardware cost, and full-day
recovery/regression thresholds.

## Updated recommendation

Keep deterministic retrieval, source identity, hot-span protection, token
accounting, and exact-source recovery in Wrench code. Train the smallest
Wrench-compatible LoRA to make bounded intent-conditioned evidence-selection
and compaction proposals. Evaluate **extractive line/segment selection**
against the full original context, and never let the model rewrite or erase
the only source copy. Start with the staged 0.8B controller; compare a 2B
controller only after a measured held-out capacity failure. Treat SWE-Pruner's
0.6B architecture as a research baseline requiring a separate pinned model
and trainer, and treat Paritok-4B as a stronger compression reference that
does not fit the current GPU envelope without a new hardware/runtime path.

The best published coding-agent results found here reach roughly 23%-54%
token reduction with minimal or improved outcomes, or roughly 72%-74% input
compression while retaining 86%-89% single-shot solve quality. These figures
do not jointly meet Wrench's >=95% task-retention and >=95% frontier-token
savings criteria. No source establishes 95% local verified completion, 5%
frontier episodes, 95% frontier-token savings, 95% all-in savings, or a
full workday of engineering for Wrench. The matched Wrench experiment remains
the deciding evidence.

No model was downloaded or loaded and no training, inference, or provider
request ran for this refresh.
