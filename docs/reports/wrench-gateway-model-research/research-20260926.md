# Local gateway model research for Wrench

Goal: [Gateway model strategy research](../../goal/wrench-gateway-model-research/GOAL.md)
Researcher: root agent, also acting as orchestrator and reviewer
Status: complete; recommendation awaits owner decision
Date: 2026-09-26 (America/Edmonton)

## Executive answer

Wrench should not try to train a 2B–9B model into a general autonomous coding
engine and call that a small-model replacement for a strong coding model. The
credible product hypothesis is a **hybrid gateway**:

1. Deterministic Wrench code performs exact reads, search, snapshots, diff
   checks, token counting, schema validation, history compaction with
   provenance, and other auditable operations.
2. A small LoRA-tuned local controller learns Wrench's bounded decisions:
   choose known evidence IDs, pick a fixed context policy, return typed
   `ENOUGH / RETRIEVE_MORE / ABSTAIN`, choose a permitted namespace or route,
   and produce source-linked short summaries where deletion is reversible.
3. A stronger model remains responsible for diagnosis, architecture, ambiguous
   requirements, multi-file semantic edits, test repair, and long-running
   engineering until actual matched tasks show the local path is non-inferior.

The best first **screen candidate**, after a bounded metadata comparison, is
`Qwen/Qwen3.5-4B` at revision
`851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a`. Its current public repository tree
lists every shard and metadata file and totals 9.34 GB. That is an upstream
snapshot inventory only, not a download admission or proof that the complete
vision-language checkpoint, a quantized copy, runtime, LoRA training, or serving
fits the current host. The candidate remains conditional on exact target-format
and storage accounting, current device inspection, model-specific LoRA/runtime
compatibility, and an independently authored screen.

There is no evidence to promise "95% of a strong model's work for 95% less."
The 0.8B test closed one role; it did not test 4B. The Wrench repository has no
eligible real matched usage pairs, so real frontier savings are still N/A. The
95/95 statement must be written as two paired measured claims: at least 95% of
the baseline's successfully completed task value, and at most 5% of its
fully-loaded cost per successful task. A reduced prompt or a local-only token
count cannot establish either.

## Question and product boundary

Could a local gateway use a LoRA-trained small controller and Wrench's
deterministic context runtime to reduce calls to a stronger coding model while
preserving end-to-end task success and a day-long engineering workflow?

This is different from the closed hypothesis that a 0.8B SLM could act as the
OpenCode primary agent or semantic controller. The new hypothesis is explicitly
bounded to routing/context behavior and verified mechanical work. It does not
transfer the old local-model approval to training, a new model, client traffic,
provider usage, or capturing real work.

Current local evidence is unusually clear about where the boundary lies:

- The tested Qwen3.5-0.8B run 02 scored 0/10 across five tool-backed semantic
  classes, with no required evidence-tool calls, five false abstentions, and
  two unsupported localization claims. Configuration facts scored 0/12
  grounded positives and 0/8 correct boundary abstentions.
- Deterministic tests passed exact line-range and literal-read mechanics, and
  one narrow synthetic patch-operation screen matched exact draft targets.
  These are exposed mechanics results. They do not prove model choices, useful
  patch semantics, or real task completion.
- A synthetic selected-context screen reported 11.64% mean input-token
  reduction on eligible examples. It did not run a downstream answer or count
  retries, fallbacks, outputs, local compute, or completed-task outcomes.
- There are zero eligible matched real frontier-usage pairs; all-in savings
  remain N/A.

The 4B checkpoint is currently the best *research starting point*, not a
verified best model. A task-specialized classifier or ranker may be smaller

evidence does not establish which architecture wins. Compare a deterministic
baseline, constrained classifier/ranker, and LoRA chat controller on the same
frozen choices rather than assuming generation is necessary.

### LoRA implications

LoRA is a plausible way to teach a model a narrow Wrench protocol. Official
Qwen training docs describe LoRA/QLoRA and explain that adapter parameters are
trained while base parameters remain frozen. This supports feasibility at the
family level, not the compatibility of the selected Qwen3.5 architecture with
Wrench's exact runtime, target modules, simultaneous core/personal adapter
composition, or 16 GB GPU budget. A third-party adapter existing is not an
engineering qualification.

The first technical gate must independently show: the exact pinned chat
checkpoint loads, tool-call parsing works, adapter target modules exist, a
tiny throwaway LoRA can save/load, the foundation hash remains unchanged, and
base+core+candidate composition matches a numerical oracle on that runtime.
Only then can a product adapter be trained. Start with a single behavior adapter
if the existing dual-adapter stack is unverified. Preserve the foundation and
known-good adapter, version every candidate, and prove rollback before
activation.

LoRA can encode routing habits and a constrained output format. It should not
hold mutable repository facts, model availability, permissions, file content,
or the current call budget. It also cannot be assumed to close a broad coding
capability gap; LoRA tuning changes the behavior within the foundation's
capabilities. The actual target labels must be reviewed outcomes from earlier
tasks, not hidden teacher reasoning, weak synthetic passes, or corrections
treated as automatically correct.

## Proposed role split

| Work | Default owner | Small model allowed when | Required control |
| --- | --- | --- | --- |
| Snapshot parsing, exact retrieval, BM25/literal search, hashes, ranges, token counts, schema checks, diff application checks | Deterministic code | Never needed | Exact identity, explicit bounds, source-linked result, fail closed |
| Candidate evidence ranking, context budget, retrieve-more vs enough, namespace discovery, whether to abstain/route | LoRA controller | Output is a finite schema over supplied IDs, with no policy/authority fields | Validate all IDs and limits; unknown or invalid output routes to baseline/escalation |
| Reversible cold-context summaries or history compaction | Controller plus deterministic compiler | Every claim links to source ranges and original bytes remain retrievable | Preserve hot source/diff/error/user instruction exactly; prove reconstruction/retrieval and omission visibility |
| Mechanical patch drafting | Small controller only as a proposal | Operation is from a reviewed finite set and a deterministic parser can independently check the exact diff | Never directly apply; code/test owner reviews; unsupported/ambiguous cases go to stronger model |
| Root-cause analysis, dependency design, multi-file semantic fixes, test repair, broad feature work, long-running task planning | Stronger coding model | Only after a separately held-out local model passes the same acceptance gate | Standard engineering sandbox, tests/review, bounded authority and human approval where needed |

Do not send repository state or user context to a hosted stronger model unless
the actual product path and data policy allow it. A local gateway does not
itself imply local end-to-end processing.

## What “95% work, 95% cheaper” must mean

Use the smart-model-only workflow as the matched baseline. The claim is eligible
only on the same task, source snapshot, permitted tools, stopping budget, and
success oracle, and only if both workflows finish the task successfully under
independent verification.

Report two primary ratios with confidence intervals:

1. **Quality retention:** `Wrench+gateway completed-task value / baseline completed-task value`.
   Predefine binary success plus severity-weighted criteria for partial work;
   do not infer value from tokens or model preferences. A 95% target requires
   the lower confidence bound to reach 0.95, with no material regression in
   task-family slices.
2. **All-in cost per successful task:** `total Wrench workflow cost / total
   baseline cost`, counting gateway inference, provider calls, retries,
   fallback, tool/schema tokens, verification, recovery, queue time where
   relevant, local energy, and amortized training/serving costs. The 95%
   cheaper target requires the upper confidence bound to be at most 0.05.

Also report success-weighted coverage, call distribution, frontier token and
dollar costs, local GPU/CPU time and energy, p50/p95 latency, interventions,
retries, safety violations, and unresolved tasks. Keep task-level paired rows
and denominator counts. If either workflow fails, show the failure; do not
exclude difficult failures to improve the ratios. Compare direct strong model,
deterministic-only Wrench, Wrench+frozen local base, and Wrench+trained LoRA
with the same strong fallback. Add a 9B only when it answers a predeclared
capacity question.

Cost arithmetic makes the ambition demanding. If a local model answers most
calls but its GPU amortization, operator time, or training/verification cost is
material, total workflow cost may remain far above 5% of the baseline. The
strong model may solve fewer calls and still dominate total cost if Wrench
adds extra attempts. Cost is a measured full-lifecycle outcome, not a property
of a small parameter count.

## Can it code all day?

An isolated benchmark score or 20-case synthetic screen cannot show sustained
engineering. A later real-task study should include multiple full workdays or
an equivalent preregistered task queue across at least three unrelated repos
and more than one language. Include bug diagnosis, scoped feature work, failing
tests, refactoring, dependency/API changes, review feedback, and long-context
compaction. Record wall-clock work, successful tasks, regressions, user
corrections, retries, context loss, process/resource restarts, and recovery.
Sample by repository/task family and time, keep held-out tasks sealed, and
measure p95 latency and cumulative local energy. A one-session soak proves
operability only; it does not replace enough independent tasks for statistical
utility claims.

SWE-bench Verified is useful historical context but no longer a sufficient
capability claim: OpenAI's 2026 audit reports contamination and test/task
design issues and recommends moving to better evaluations. SWE-bench Pro
targets longer-horizon work, and Terminal-Bench targets complex terminal tasks,
but neither substitutes for matched Wrench workflow and owner-repository
outcomes. Public benchmarks are evaluation-only and their exact versions,
scaffolds, commit dates, and task availability must be pinned.

## Proposed staged experiment

No stage below is run or admitted by this research report.

### G0: freeze protocol and candidate identity

- First inspect the actual training/serving device and aggregate Wrench storage.
- Pin the selected upstream full commit; enumerate each shard, index,
  tokenizer/config/template/license file, checksum and byte size.
- Choose a single format and enumerate its source/quantized/runtime copies,
  peak conversion/download space, training state, output adapter, retained
  good versions, logs, and backup. Use the strict storage checker and reserve
  before every artifact-producing job.
- Verify current serving and LoRA libraries, exact Qwen3.5 architecture
  support, 10% RAM/VRAM reserve, output schema, tokenizer/parser identity, and
  5 GB projected destination-volume reserve.
- Preregister task families, controls, gates, splits, sample-size reasoning,
  all-in cost conversions, and abort criteria. Do not use any exposed local
  acceptability screen as fresh train/dev/test data.

### G1: mechanical fast paths without an SLM

Implement/evaluate exact supported operations as deterministic functions.
Retain the current measured narrow envelope as mechanics-only. Create fresh
fixtures, bind input IDs/hashes and exact output oracles, and add missing/stale,
ambiguous, over-budget, adversarial, and long-hot-context cases. No generated
natural-language success claim.

### G2: local controller ablation and LoRA

On new approved, source-derived fixtures, compare deterministic selection,
frozen 4B outputs, and a LoRA-trained 4B controller. Teach finite decisions
over retrieved source IDs and a stable Wrench tool schema. Freeze base/core;
hold out repository groups and later time. Keep an untouched regression set and
zero authority violations as a mandatory gate. The local model is accepted
only if it has a reproducible held-out gain over deterministic selection after
its latency/resource cost, while matching safety and outcome floors.

If it does not improve a deterministic mechanism, remove that learned step. Do
not increase size automatically. The next model may be 9B only if a prespecified
capacity hypothesis predicts and justifies it.

### G3: full task replay and long-run operation

After E0–E3 prerequisites and the gateway route are actually integrated,
preregister a consented matched replay: direct stronger model vs deterministic
Wrench+same strong model vs Wrench+LoRA controller+same fallback. Use real
eligible engineering tasks with verified outcomes, and count every request,
retry, repair, fallback, local computation, test and session artifact. Follow
the existing E4 template and approval rules. Do not collect or transfer user
work until per-task consent and the required policy approvals exist.

Stop if source/model identity is incomplete, a weight/active adapter changes,
the 10% resource reserve or 50 GB aggregate is breached, an output violates
authority, a fallback call cannot be accounted for, an adapter regression
breaks core behavior, or a cost/quality ratio misses its frozen gate. Stop
instead of tuning on exposed final data.

## Decision requested

The evidence supports exploring Wrench as a deterministic context/mechanics
gateway with a narrow LoRA controller and a stronger-model fallback. It does
not support replacing a smarter coding model with a small one, nor the 95/95
claim. The owner should decide whether to authorize G0 and a new candidate
screen. If approved, the next action is a no-model artifact/runtime admission
plan, then the smallest compliant 4B compatibility check. Do not download,
train, route, spend, or capture real tasks until their separate gates and
authorities are satisfied.
