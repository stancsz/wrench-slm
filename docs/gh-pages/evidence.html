A result you can inspect here

The site’s example receipt is generated by calling the actual Python verifier on a temporary fixture. It records a successful line read, a rejected path escape, a rejected shell action, and an unchanged fixture.

Its scope is deliberately small: direct verifier behavior. It measures neither model quality nor end-to-end cost savings. The getting-started guide explains how repository collaborators can reproduce it.

What the internal project record shows

The project repository is public. The following is a maintainer summary, not an independent reproduction or a complete public benchmark. Consult version-specific records and reproduction conditions when assessing a claim.

  • A bounded local operational shadow recorded 200 of 200 mechanical requests, with concurrency, cancellation recovery, resource checks, and receipt hashing. It does not establish production resilience.
  • A guided fallback experiment passed both direct clients and all three hybrid clients. Its recorded token usage lacks the complete provider-authoritative paid-cost evidence needed for a savings claim.
  • Per-client timing instrumentation has been added. Repeated matched latency distributions still need to be collected; a single process duration is insufficient.

What counts as savings

Run the same authorized workload through the stronger-model baseline and through Wrench with fallback. Compare completed-task correctness, safety, latency, cloud tokens, local work, actual cost, retries, corrections, and fallback overhead.

Net cost savings =
  baseline cost for the matched successful workload
  − total hybrid cost for that same workload

Total hybrid cost includes paid model use and relevant local overhead. Fewer cloud tokens do not always mean a lower invoice, especially with flat subscriptions, cached pricing, or retries. Faster refusals do not count as faster completed tasks.

The target, clearly labeled

The current North Star targets at least 95% net frontier-token savings on the bounded evaluated workload, after accounting for verification, compaction, retries, corrections, and fallback. It also requires no material regression in final success or safety and meaningful successful-task latency improvement.

95% is a project target. It is not an achieved general result, a discount on your subscription, or a promised reduction in your AI bill.

The homepage’s 20× expresses that same target: at most 1/20 of baseline frontier-token usage. The newer < 0.5% ambition concerns cloud-model spending on the same successfully completed workload, compared with a cloud-model baseline. It is a separate, longer-term aspiration, not the current acceptance gate or a measured result. Total cost comparisons must still include local overhead.

The 4M message describes a large-input direction using local retrieval and compaction. It does not establish native 4M attention, complete recall, or an end-to-end latency guarantee.

What comes next

  1. Finish a matched real-workflow comparison with an accepted fallback candidate and complete cost accounting.
  2. Repair timeout and latency outliers, then collect repeated successful-task timings.
  3. Expand only the safe handlers justified by actual fallback volume.
  4. Continue sustained operational checks before considering production enablement.
