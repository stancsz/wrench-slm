02 / The workflow

Small jobs, checked locally.

Think of Wrench as a narrowly scoped helper inside a coding workflow. It supplies evidence for the parts it can verify and hands back the rest.

An everyday example

You ask your coding assistant to understand a timeout. The overall task needs reasoning. One step may simply be reading the relevant configuration. Wrench’s role is that bounded step: retrieve the setting, check the request, and return the evidence. Diagnosing the whole failure remains with the larger workflow.

Avoiding a model call for a file read does not automatically reduce the whole task’s bill. The useful comparison is the same successfully completed task, including the work needed to prepare, verify, and recover from local attempts.

How is this different from a coding model?

Wrench is built to complement larger models and reduce total workflow cost. Coding models typically address broader programming tasks and can use tools and test feedback. Wrench narrows its scope to steps that can be described precisely and checked independently. They can work together.

TaskCoder / larger modelWrench’s bounded part
Investigate a login timeoutForm hypotheses, diagnose the cause, and propose a fix.Read specified configuration and search for exact error text.
Prepare a code changeChoose an approach and reason about dependencies across files.Prepare a bounded patch draft within supported scope for human or workflow review.
Work with a long historyReason from relevant evidence.Retrieve paths, symbols, and passages with traceable sources.
Handle uncertain or out-of-scope requestsThe surrounding workflow decides whether to reason further, ask, or stop.Abstain and return control without expanding its authority.

Dependability here comes from specific mechanisms: construct known arguments in code, verify proposals independently, bound execution authority, retain evidence, and hand off failures. These reduce the scope for free-form generation and unrestricted actions. Coding models can be paired with similar systems; Wrench must demonstrate value by making this division of work effective and measuring the benefit.

Abstention is a handoff, not a score to maximize

An abstention means: “This step exceeds my scope or authority, or did not pass verification. The caller must take over.” It is a machine-readable outcome. The caller preserves the original request and arranges its configured fallback or another response.

Today, explicit rules and verification boundaries primarily determine this outcome. We should not present it as a model that has learned perfectly calibrated confidence. Learned free-form routing remains disabled. If every request is declined, Wrench may just add latency and cost before the larger model does the work.

Evaluation must therefore measure correct completion of eligible steps, prohibited accepts, final task success, and total latency and cost including retrieval, verification, retries, and fallback. A simple rules-plus-fallback baseline is also necessary to show that Wrench adds useful value. See the current evidence and evaluation boundaries.

For a coding model with agent and tool-use capabilities, see the official Qwen3-Coder introduction. The table describes our division of work, not a model performance ranking.

What happens to a request

  1. Receive the task and its allowed scope. Keep the current request separate from old context.
  2. Find relevant evidence. Local retrieval and search reduce the amount of material that needs further processing.
  3. Propose one bounded action. A clear mechanical request can use deterministic rules. Learned free-form routing is currently disabled.
  4. Verify independently. Check the action, allowed root, parameters, and limits before execution.
  5. Return a result or decline. The client protocol pairs the proposal with a final answer bound to the verified result. If the request cannot be handled, the surrounding workflow can use its configured fallback.

Where the boundary sits

Wrench has no arbitrary shell action, autonomous write action, or credential-access action. General feature implementation, database migrations, deployments, and multi-step debugging are outside this worker’s scope.

An abstention means “this request cannot be handled within this boundary.” It is a signal for the caller, not a successful task completion. The caller must preserve the original request and handle fallback explicitly.

An allowed directory is still a real permission boundary you configure. Use a dedicated, non-sensitive fixture for evaluation. A file reader is not a secrets classifier. If you enable a cloud fallback, review what context the surrounding client sends to that provider.

What “large context” means here

Wrench can use retrieval and compaction to work with large input collections while keeping model work bounded. This does not mean a small model attends to millions of tokens at once, or that it understands every detail of a large repository.
