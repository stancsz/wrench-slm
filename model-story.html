Build notes / From Qwen to Wrench

How this little
wrench was built.

Start with Qwen3.6. Select and prune experts. Try LoRA fine-tuning. Add tools and an independent checker. Here is what each step means, including the parts that did not work well enough.

Where things stand: pruning and fine-tuning have real experiment records, but no standalone small model has passed every production gate. The active path combines deterministic tools, retrieval, and verification. Learned free-form tool routing remains disabled. This page documents past model work; it does not restart training.

This is an overview of several experiments, not a claim that one model version has completed every stage successfully.

01. Start on Qwen’s shoulders

I began with the official, unquantized Qwen3.6-35B-A3B weights. Qwen supplies the pretrained foundation. Wrench explores making a derivative smaller and more focused on bounded developer tasks.

The model uses MoE, or mixture of experts. Think of a workshop with many teams: each layer has 256 routed experts, and each token selects 8 of them, alongside a shared expert. An expert is a neural-network computation module, not a neatly labeled department for coding or jokes.

Using a few experts at a time does not remove the cost of storing the others. The original model still carries a large expert bank. If we only want a narrow set of jobs, could we carry fewer experts?

02. Prune experts: carry a smaller bank

The first structural experiment simply kept experts 0 through 7 in every layer and checked that the result could load and generate. After that, selection became guided by recorded router activity.

  1. Run representative prompts through the original model. An early profile used 20 developer-task prompts covering reads, search, status, abstention, and related cases, recording how often each layer selected each expert.
  2. Rank experts separately for each layer. Keep the most frequently selected ones, breaking ties by original expert ID. Experiments retained 8, 16, or 32 experts, with a later 10-expert candidate. Twenty prompts are an early sample, not coverage of every real workflow.
  3. Physically slice the weights. Copy the selected expert tensors and matching router rows into a new Safetensors checkpoint, then update its configuration. Preserve the original source and copy the other tensors unchanged at this stage.

The early 8-expert structural candidate had about 3.88 billion parameters; the 16-expert candidate had about 4.89 billion. These describe particular historical candidates, not a universal Wrench specification or a GPU memory requirement.

Two different knobs: retaining 8 experts shrinks the bank; activating 8 experts per token controls how many participate in a computation. The source already activated 8 routed experts. Going from 256 stored experts to 8 does not establish a 32× speedup, and removing experts can remove useful capabilities.

03. LoRA: teach the smaller model its job

A smaller model does not automatically follow our rules. We need a checkable work order: which file, which lines, or a clear refusal when the request falls outside its authority.

LoRA fine-tuning trains a small set of additional parameters. Think of it as a learnable patch beside mostly frozen original weights. Some Wrench experiments also directly update router parameters so the smaller model can adapt to its task.

  • Training examples: pair requests with explicit target outputs, including allowed tool tasks and cases that must be declined.
  • What changes: experiments have tried output-head and attention LoRA with distinct configurations. These are historical experiments, not a feature installed in every version.
  • How learning is checked: compute training loss on target-answer tokens, use development cases to inspect results, and keep the sealed final evaluation split out of training and tuning.
One actual training configuration

Phase 130 used 456 development-only boundary calibration rows, 400 training steps, and a 0.0003 learning rate. Attention and output-head LoRA used rank/alpha 8/16 alongside router updates, totaling 4,460,544 trainable parameters. Rank is the adapter’s internal dimension, not its expert count. This is a historical experiment, not a launch recipe recommended for every device.

04. Better scores were not enough

In that attention-LoRA experiment, expected-outcome matches on 220 historical cases rose from 62 in the baseline to 138. But prohibited accepts also rose from 6 to 14: cases that should have been declined were accepted. The candidate failed the safety gate and was not promoted to production.

Later experiments constrained decoding to valid JSON. That could contain syntax errors without preventing invented paths or incorrect tool arguments. A neatly filled form can still be the wrong work order.

The current approach therefore uses deterministic code for fields that can be extracted precisely from requests and evidence. A learned component must demonstrate added value before it joins the working path.

05. Merge and quantize: pack lighter

A LoRA adapter can be merged into a new checkpoint, avoiding Python-level adapter overhead during serving. Separate experiments also produced W4A16 quantized exports: represent suitable weights with fewer bits while keeping activations at 16 bits. This saves storage, but numerical error and runtime support still need checking.

Early text-only NVFP4 packs measured about 3.19 GiB for 8 experts and 3.72 GiB for 16 experts. Both passed a single-request CUDA load/generation smoke. Those are historical file sizes, not current release promises or sustained VRAM requirements. The quantization exports and LoRA runs above belong to different stages; they must not be combined into a claim about one verified final artifact.

Running a model also needs caches, intermediate computations, and runtime libraries. A small download is only part of making an older machine comfortable to use. See the small-GPU and older-phone roadmap.

06. Today: tools do the legwork, larger models handle the hard parts

The focus is now the whole workflow. When an assistant investigates a timeout, the small step of reading a timeout setting can follow this path:

  1. Receive the request and its boundaries. Establish the allowed directory, action family, and input.
  2. Find relevant evidence. Locate paths, symbols, errors, and nearby passages in files or long histories, retaining their sources.
  3. Build an explicit work order. Construct known arguments deterministically, such as the file and line range to read.
  4. Check it independently. The verifier checks the action, path boundary, size limits, and other constraints.
  5. Execute within limits and bind the result. A restricted executor performs allowed reads; patches remain review-only drafts. The client’s subsequent answer must bind to the verified tool result.
  6. Hand off when necessary. The caller’s configured fallback can send relevant evidence to a stronger model for further reasoning. This does not give the local worker arbitrary shell or file-writing authority.

The 4M-input direction uses the same principle: accept, preserve, and search a large collection, then select relevant passages for a bounded working context. It is closer to using an index and opening relevant pages than reading every page simultaneously. It does not establish native attention over four million tokens or perfect retrieval.

The useful score is the total cost of the same successfully completed task: frontier tokens, local work, retries, and corrections included. Expert counts and training loss cannot establish those savings by themselves.
