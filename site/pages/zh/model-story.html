技术手记 / 从 Qwen 到 Wrench

这把小扳手，
到底怎么造的？

从现成的 Qwen3.6 出发，挑专家、做裁剪、用 LoRA 补课，再给它配上工具和检查员。下面把这条路摊开讲，不用先读完一本深度学习教材。

先说清进度：裁剪和微调都有真实实验记录，但还没有得到一个通过全部生产门槛的独立小模型。目前主线是确定性工具、检索和验证组成的混合流程；自由生成工具参数的学习式路由保持关闭。本文回顾模型实验，不代表重新启动训练。

  2. 02 / 减重专家裁剪缩小专家库
  3. 03 / 补课LoRA 微调练具体任务

这是几条实验路线的总览，不是某一个模型版本已经全部通关的流水线。

01. 先站在 Qwen 的肩膀上

我从 Qwen3.6-35B-A3B 的官方未量化权重开始。预训练的底子来自 Qwen；Wrench 做的是在这个底子上，尝试把范围收窄、体积压小，专门处理开发中的小任务。

它用的是 MoE，混合专家。可以把它想成一个有许多小组的车间：每层有 256 个可选择的专家，每个 token 会选中其中 8 个，另有一个共享专家参与。这里的“专家”是神经网络里的计算模块，不是一个负责写代码、另一个负责讲笑话的真人部门。

少量专家上班，不等于只要存少量专家。原模型仍要保存庞大的专家库。于是问题来了：如果只接一小类活儿，能不能少带一些专家出门？

02. Prune experts：给专家库减重

第一版先做最朴素的结构实验：每层保留编号 0 到 7 的专家，检查裁完能不能加载、能不能生成。能跑之后，再改成根据实际路由记录挑专家。

  1. 先让原模型做样题。早期用 20 条开发任务提示，覆盖读文件、搜索、状态查询和拒绝越界等场景，记录各层专家被选中的次数。
  2. 每层分别排名。按使用次数挑出要保留的专家；次数相同就按原编号排序。试过保留 8、16、32 个的版本，后来也做过 10 个的实验。20 条提示只是早期样本，不能代表所有真实任务。
  3. 真正裁掉权重。把专家权重和对应的路由器行一起切出来，更新配置，写成新的 Safetensors 权重文件。原始 Qwen 权重保留不动，其余张量在这一步原样复制。

早期 8 专家结构版本实际约 38.8 亿参数，16 专家版本约 48.9 亿。这两个数字是当时结构候选的统计，不是所有 Wrench 版本的统一规格，也不是显存需求。

一个容易绕晕的区别：“保留 8 个专家”是缩小仓库；“每个 token 激活 8 个专家”是决定一次叫几个人干活。原模型本来就激活 8 个，所以不能把 256 → 8 直接宣传成推理快了 32 倍。裁剪也可能把有用能力一起裁掉。

03. LoRA：减完重，还得补课

裁小了，不代表它就会按我们的规矩干活。我们要的也不是一段听起来很像答案的话，而是一份能检查的工作单：读哪个文件、哪几行；或者明确说“这活儿不在我的权限里”。

LoRA 是一种只训练少量新增参数的微调方法。可以理解成给原模型加一份可学习的小补丁。大部分原始权重冻结，只调整补丁；Wrench 的一些实验还会直接更新路由器参数，让缩小后的模型重新适应任务。

  • 教什么：任务和明确的目标输出成对出现，既有允许做的工具任务，也有应该拒绝的边界案例。
  • 改哪里：尝试过输出头 LoRA 和注意力 LoRA，具体配置各不相同，也不代表每版都装了这些方案。
  • 怎么练：训练时主要针对目标答案计算损失。开发集用于检查效果，封存的最终测试集不参与训练和调参。
给想看配置的朋友：一次真实的训练长什么样？

Phase 130 使用 456 条开发用途的边界校准数据，训练 400 步，学习率 0.0003。注意力和输出头 LoRA 的 rank/alpha 为 8/16，同时更新路由器，共 4,460,544 个可训练参数。rank 是补丁的内部维度，不是专家数量。这是一条历史实验配置，不是推荐给所有设备的启动参数。

04. 真正的转折：分数涨了，也不能放行

那次注意力 LoRA 实验中，220 个历史案例的预期结果匹配数，从基线的 62 个升到 138 个。但测试里本该拒绝却被接受的案例，也从 6 个升到 14 个。这是失败信号，这个候选没有被晋升为生产版本。

后来也试过约束模型只能输出合法 JSON。括号能对上，文件路径仍可能编错；格式整齐，工作单也可能开错。会填表，和把事情做对，是两回事。

所以现在不再要求小模型自由生成每一个路径和参数。能从请求和证据里准确提取的部分，交给确定性的程序；模型实验必须证明自己增加了价值，才有资格进入工作流程。

05. 合并、量化：把行李收小一点

LoRA 补丁可以合并进一份新的权重，服务时就不用逐层外挂 Python 补丁。另一些实验还做了 W4A16 量化：对适用的权重用更低位数表示，激活保持 16 位。可以理解成换一种更省空间的数字记法，也需要检查误差和运行支持。

早期文本专用的 8 专家 NVFP4 包约 3.19 GiB，16 专家包约 3.72 GiB，都做过单请求 CUDA 加载和生成检查。这些是特定历史导出的文件大小，不是最新版本的承诺，也不是持续运行所需的显存。量化导出和上面的 LoRA 实验来自不同阶段，不能拼成同一份已验证成品。

真正运行还要放缓存、中间计算结果和运行库。“下载包小”到“你的旧电脑跑得舒服”，中间还有作业要交。小显存和旧手机的目标在这里。

06. 今天的方案：小工具干活，大模型解难题

现在的重点，是把整个工作流程做好。比如你让助手查一个超时问题，其中“读出配置里的 timeout”这一步，可以走下面这条路：

  1. 拿到任务和边界。确认允许访问的目录、操作类型和输入。
  2. 找到相关证据。从文件或长历史中定位路径、符号、报错和附近内容，留下出处。
  3. 构造一份明确的工作单。例如读取指定文件的指定行，参数能确定就用程序构造。
  4. 由独立验证器检查。操作是否允许、路径是否越界、大小和行数是否超限。
  5. 受限执行，绑定结果。读文件等动作由受限执行器完成；补丁只给草稿。客户端后续答案须绑定已验证的工具结果。
  6. 搞不定就交接。由调用方按配置把必要证据交给更强的模型，继续推理。小工具不会因此获得随意执行命令或写文件的权限。

4M 大输入也走这个思路：先接收、保留和检索大批资料，再提取有用片段送进有限的工作窗口。像先查目录，再翻相关页。它不表示小模型一次原生注意力计算就读懂了 400 万 token，也不保证每条线索都能找全。

最后要算的是同一件事成功做完的总账：强模型用了多少 token，本地花了多久，有没有重试和返工。裁了多少专家、训练损失多低，都不能单独当作省钱证明。
